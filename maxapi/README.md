# Max Bot API — TypeSpec-описание

Рукописное [TypeSpec](https://typespec.io)-описание Bot API мессенджера
[MAX](https://dev.max.ru/docs-api), версия **0.0.33**: 129 схем и 29 операций
(17 путей), из которых компилятор `@typespec/openapi3` генерирует
OpenAPI 3.0. Каждая модель, каждое поле и каждое ограничение перенесены
вручную с построчной сверкой против официальной схемы — не автогенерация и
не reverse-engineering по документации, а транскрипция first-party контракта
в TypeSpec с последующей семантической проверкой эквивалентности.

## Как собрать

```bash
make install   # один раз: npm-зависимости и кодогенераторы
make           # всё остальное
```

**Работайте через `make` без аргументов.** Эта цель пересобирает контракт из
`*.tsp`, публикует его в корень, проверяет требования КБ, перегенерирует Go-
структуры обоими генераторами и прогоняет тесты — свои и обоих примеров.

Всё разом не для удобства, а по необходимости: в git лежат оба конца цепочки.

```
*.tsp  →  openapi.MaxBotApi.yaml     ← читает валидатор на периметре
                    ↓
              models.go              ← читает бот
```

Обновить их порознь — значит выдать валидатору и боту разные версии
контракта. Ни компилятор, ни тесты этого не заметят: по отдельности оба файла
корректны. Отдельные цели (`build`, `gen`, `validate`) остались для отладки,
но повседневная команда одна.

`make check-sync` — та же перегенерация плюс вопрос к git: изменилось ли
что-нибудь. Если да, значит в коммите лежали артефакты, не соответствующие
`*.tsp`. Место этой цели — CI и pre-push: единый шаг делает рассинхрон
маловероятным, но не невозможным, а поймать его должна машина, а не
дисциплина.

`install` состоит из двух частей. Пакеты TypeSpec и quicktype ставит npm, их
версии держит `package-lock.json`. Бинарь `oapi-codegen` ставит
`scripts/install_tools.py` обычным `go install` — туда, куда его кладёт Go
(`$GOBIN`, а если тот пуст, `$GOPATH/bin`), — и сборка вызывает его по имени.

Отдельный этап, а не `go run пакет@версия` в шаге сборки, по трём причинам:
`go run` ходит в сеть при каждом вызове, что неприемлемо для закрытого
контура; версия оказывается вписанной в команду, а команд две (Makefile и
package.json) и разойтись им ничто не мешает; подменить версию для проверки
нечем, кроме правки обеих.

Версия закреплена один раз, в самом скрипте. Скрипт идемпотентен, сверяет
именно версию установленного бинаря (а не наличие файла — иначе обновление
закрепления не доехало бы туда, где бинарь уже стоит) и проверяет, что каталог
установки виден в `PATH`, подсказывая нужный `export`.

`build` — это `tsp compile .` и семь постобработок результата, каждая из
которых компенсирует то, чего эмиттер `@typespec/openapi3` не умеет — либо
вовсе, либо через `tspconfig.yaml`. Порядок значим: каждая работает по
результату предыдущей.

1. `scripts/seal_additional_properties.py` — `additionalProperties: {not: {}}`
   → литеральный `false`;
2. `scripts/fill_inherited_stubs.py` — раскрытие пустых стабов `prop: {}`,
   которыми `seal-object-schemas` перечисляет у наследника унаследованные
   свойства (см. «Требования КБ» ниже);
3. `scripts/apply_int_bounds.py` — явный `maximum` целочисленным схемам, где
   его не задал автор: компилятор TypeSpec держит числовые литералы в
   JS-числах, поэтому `@maxValue` выше 2^53−1 теряет точность и эмиттер молча
   выбрасывает ограничение. Единственное такое поле — `MessageBody.seq`,
   которому нужен полный диапазон `int64`;
4. `scripts/prune_unused_schemas.py` — удаление схем, до которых нет ссылок
   (требование SCHEMA-валидатора «Potentially unused component»): эмиттер
   выводит каждую модель namespace-а независимо от достижимости;
5. `scripts/flatten_discriminated_unions.py` — перевод полиморфизма из
   `allOf`-наследования в каноническую форму OpenAPI `oneOf` +
   `discriminator` (см. «Дискриминированные union'ы» ниже);
6. `scripts/strip_nullable_wrapper_type.py` — снятие `type: object` у
   nullable-обёрток `{allOf: [$ref], nullable: true}`: его ставил эмиттер по
   букве OAS 3.0.3, а срабатывало на него правило КБ [59], которое на обёртке
   выполнить нельзя (см. «Где нет `additionalProperties: false`» ниже);
7. `scripts/annotate_composites.py` — комментарии к оставшимся композитным
   позициям: у каждой буква случая и причина, в начале файла — блок с полным
   разбором, подсчётом и пометками «В ОРИГИНАЛЕ» (какими схемами то же самое
   записано у MAX; цифры и перечень схем считаются по
   `reference/max-openapi-official.json`, а не вписаны руками). Идёт
   последним, потому что описывает уже итоговый документ. Комментарии
   YAML-парсерами игнорируются: ни на сверку, ни на `kin-openapi` в `maxmoc`
   они не влияют.

Седьмым шагом `scripts/publish_openapi.py` копирует готовое из
`tsp-output/@typespec/openapi3/` в корень `maxapi/`. Каталог эмиттера
промежуточный и целиком в `.gitignore`: до конца конвейера лежащий там YAML
ещё не контракт. В git попадают именно корневые копии — их и читают
потребители.

Результат — два OpenAPI 3.0 документа в `maxapi/`:

- `openapi.MaxBotApi.yaml` — сам Max Bot API, эквивалентный по составу
  путей/схем официальной спецификации (с точностью до осознанных отличий,
  см. ниже);
- `openapi.MaxBotWebhook.yaml` — контракт webhook-эндпоинта, который
  реализует **разработчик бота** (см. раздел «Как реализовать
  webhook-сервер»). Официального аналога не имеет и сверке не подлежит.

## Go-структуры

```bash
make gen-quicktype     # либо: npm run gen:quicktype
```

Даёт Go-модуль `maxapi` в `gen/quicktype/` — 110 структур и 56 enum-типов,
покрывающих все 117 схем контракта плюс `WebhookUpdate` и `UpdateUnified`
из webhook-документа. Пакет намеренно состоит из одних типов: HTTP-клиент и
webhook-сервер пишутся поверх него вручную.

Цепочка: `openapi.MaxBotApi.yaml` → `scripts/openapi_to_jsonschema.py` →
`gen/max.schema.json` → `quicktype` → `scripts/finalize_go_models.py` →
`gen/quicktype/models.go`.

Переходник нужен потому, что quicktype не умеет OpenAPI: его входные языки —
`json`, `schema`, `graphql`, `postman`, `typescript`. Он же закрывает пять
расхождений OpenAPI 3.0 и JSON Schema — снятие `additionalProperties: false`
(на нём quicktype падает в связке с `allOf`), перевод `nullable: true` в
«или null» (иначе поле стало бы значением, а не указателем), удаление
`discriminator`, схлопывание обёрток `{allOf: [{$ref: X}]}` обратно в `$ref`
(иначе одна схема размножается в несколько Go-типов) и «конверт» на корне
(без него quicktype не именует схемы и схлопывает `oneOf`). Подробности с
цифрами — в докстринге `scripts/openapi_to_jsonschema.py`.

**Дискриминированные union'ы плоские.** `Update`, `Attachment`, `Button`,
`MarkupElement`, `ReplyButton` — это структуры, в которых собраны поля всех
вариантов, необязательные; вариант определяется полем-дискриминатором
(`update_type` или `type`). Варианты существуют и отдельными типами
(`MessageCreatedUpdate`, `PhotoAttachment`, …), но `UnmarshalJSON` с
диспетчеризацией по дискриминатору quicktype не порождает — это пишется в
потребителе.

`gen/quicktype/models_test.go` закрепляет разбор тела, записанного с живого Max:
разрядность `seq` (значения порядка 1.17e17 — выше JSON-safe 2^53−1),
указатели у `nullable`-полей, полиморфное вложение и round-trip.

### Два варианта кодогенерации

В репозитории временно лежат оба, чтобы выбрать по факту, а не по описаниям:

| | `gen/quicktype` — quicktype | `gen/oapi-codegen` — oapi-codegen |
|---|---|---|
| Читает контракт | нет, нужна промежуточная JSON Schema | да, напрямую |
| Рукописных строк между контрактом и Go | 185 | 0 |
| Схем без своего типа | 7 | 2 |
| Искажённых имён | 2 | 0 |
| Зависимостей | 0 | 3 |
| Union'ы | плоские, разбор в два шага | `ValueByDiscriminator()` |
| Строк | 2755 | 5051 |
| **Рукописного кода в примере** | **379** | **377** |

Оба настроены на одно и то же — только модели. Клиент oapi-codegen генерировать
умеет (`client: true`, ещё 3344 строки и 20 методов), но у quicktype клиента
нет вовсе, и с включённым сравнивались бы разные вещи.

```bash
make gen          # оба варианта
make compare-gen  # оба + таблица выше, посчитанная по факту
```

Таблицу печатает `scripts/compare_generators.py`, машиночитаемая копия —
`gen/compare.json`. Оба варианта проверяются одним и тем же телом, записанным
с живого Max, — иначе сравнивать нечего.

Последняя строка — главная. Два примера в `example-quicktype/` и `example-oapi-codegen/` решают
одну задачу на одинаковых тестах, и разница вышла в **две строки из 379**:
файлы клиента совпадают построчно (различаются лишь `sub.Url` против `sub.URL`),
`cmd/echobot` совпадает полностью, различается один метод `dispatch()`. То есть
по объёму рукописного кода генераторы неразличимы, и выбирать по нему нельзя.

Главное различие — не в цифрах, а в форме. Вариант quicktype требует
переходника, который переписывает семантику OpenAPI (`nullable`,
`additionalProperties`, обёртки `allOf`) вручную: это второе, независимое
прочтение контракта, и его ошибки не роняют сборку. Пример спящей: узел
`{type: string, enum: [...], nullable: true}` переходник переведёт в
`{type: [string, null], enum: [...]}`, где `enum` не содержит `null` — то есть
nullable потеряется молча. В нынешнем контракте таких полей ноль.
А вот действующий: необязательный nullable-массив `NewMessageBody.attachments`
quicktype отдаёт как `[]AttachmentRequest` с `omitempty`, и пустой массив
пропадает вместе с `nil` — «удалить все вложения» в `PUT /messages` на этом
варианте не выразить. У oapi-codegen там `*[]AttachmentRequest`: `nil`
опускается, `&[]AttachmentRequest{}` уходит как `[]`.
Вариант oapi-codegen читает тот же YAML, что уходит на валидатор периметра, и
второго прочтения не заводит.

Цена — три зависимости в рантайме (`oapi-codegen/runtime` и две косвенные)
против нуля у quicktype, что заметно при переносе в закрытый контур, и
указатель на слайс (`*[]Attachment`) у необязательных массивов.

## Роли методов: приём и отправка

Помимо официальных тегов (`bots`, `chats`, `messages`, `subscriptions`,
`upload`) операции размечены дополнительным сквозным тегом:

- **`bot-sending`** — минимальное ядро исходящих вызовов для типичного бота:
  `getMyInfo`, `sendMessage`, `editMessage`, `deleteMessage`,
  `answerOnCallback`, `sendAction`, `getUploadUrl`, `getChat`,
  `getMembership`, `getPinnedMessage`, `pinMessage`.
- **Приём событий** отдельного тега не требует — это в точности официальный
  тег `subscriptions`: `subscribe`/`getSubscriptions`/`unsubscribe`
  (webhook) и `getUpdates` (long polling, только для разработки).

## Как реализовать webhook-сервер

Полный машиночитаемый контракт — `webhook.tsp` → `openapi.MaxBotWebhook.json`
(можно скормить генератору серверных заглушек). Словами:

1. Поднимите HTTPS-эндпоинт на порту 443 с сертификатом доверенного центра
   (HTTP и самоподписные сертификаты не поддерживаются с 25 мая 2026).
2. Зарегистрируйте его: `POST /subscriptions` с `url` и, желательно,
   `secret` (5–256 символов, `A-Za-z0-9_-`). Путь эндпоинта в контракте —
   `/max/v1.0/webhooks/{integrationId}`, где `integrationId` — идентификатор
   интеграции: строка с `format: uuid`, ровно 36 символов, hex-группы
   8-4-4-4-12 через дефисы. Регистрируемый `url` должен оканчиваться этим
   путём.
3. Платформа шлёт на ваш URL `POST` с `Content-Type: application/json`;
   тело — событие (тип в поле `update_type`, 16 вариантов:
   `message_created`, `message_callback`, `bot_started`, …). В
   `openapi.MaxBotWebhook.json` тело операции — `anyOf` из двух
   эквивалентных представлений на выбор:
   - **`UpdateUnified`** — единая «плоская» схема в стиле Telegram Bot API:
     общие поля обязательны, все вариативные опциональны, у каждого в
     описании указано, при каких `update_type` оно приходит. Один класс на
     все события — просто десериализовать.
   - **`WebhookUpdate`** — строгий `oneOf` из 16 конкретных типов для
     типизированной кодогенерации, с `discriminator` по `update_type`:
     валидатор сразу переходит к нужному варианту и называет виноватое
     поле вместо `doesn't match any schema from "anyOf"`.
   Если задан `secret`, он приходит в заголовке `X-Max-Bot-Api-Secret` —
   проверяйте его.

   Примечание про линтеры OpenAPI: предупреждения «Definition was declared
   but never used» в выводе больше не появляются — недостижимые схемы
   вычищает `scripts/prune_unused_schemas.py` (требование SCHEMA-валидатора
   «Potentially unused component»). Среди вычищенных есть и сироты самой
   официальной спецификации — `BotPatch`, `PhotoTokens`: в 0.0.33 таких
   сирот восемь. В
   `openapi.MaxBotWebhook.json` четыре (`BotInfo`, `BotCommand`,
   `ChatMember`, `ChatAdminPermission`) — наследники используемой
   `UserWithPhoto`, которые эмиттер включает вместе с родителем.
4. Отвечайте `200 OK` как можно быстрее; обработку события выполняйте после
   ответа, затем вызывайте нужные методы `bot-sending`.

## Как сверить с официальной схемой

```bash
python3 scripts/compare.py
```

Скрипт разворачивает `$ref`/`allOf` в обоих документах (наш и
`reference/max-openapi-official.json`) и сравнивает по сути: пути и
операции, `operationId`, теги, параметры, тела запросов/ответов, свойства
схем и их ограничения (`type`, `format`, `enum`, `required`, `nullable`,
`default`, `maxLength`, `minLength`, `maximum`, `minimum`, `maxItems`,
`minItems`, `pattern`), дискриминаторы и их `mapping`. Имена схем считаются
соответствующими друг другу по договорённости (в проекте они совпадают с
официальными 1:1).

Каждая найденная разница печатается одной из двух меток:

- **`DIFF`** — непредвиденное расхождение. Наличие хотя бы одной строки
  `DIFF` даёт `sys.exit(1)` — это красный флаг: либо в TypeSpec закралась
  ошибка, либо появилось новое (пока не задокументированное) отличие от
  оригинала.
- **`KNOWN`** — расхождение, подпадающее под один из regex-паттернов в
  списке `DEVIATIONS` в `scripts/compare.py`. Это осознанные,
  задокументированные отличия (см. таблицу ниже) — каждой строке `KNOWN`
  соответствует пояснение либо прямо в комментарии рядом с паттерном в
  `compare.py`, либо в этом README.

Финальная строка — `Итого: N расхождений, M известных отличий`. Текущее
состояние: **8 расхождений, 1485 известных отличий** — см. раздел «Статус».
Все восемь — отсутствующие пути `/chats*`: `routes/chats.tsp` намеренно не
подключён в `main.tsp`.

## Осознанные отличия от официальной схемы

Ниже — полный перечень мест, где наш TypeSpec намеренно не воспроизводит
официальную схему буква в букву, и почему. Формулировки согласованы с
комментариями рядом с соответствующими regex-паттернами в
`scripts/compare.py` (эти комментарии — источник истины; здесь —
человекочитаемый пересказ).

| # | Что | Почему |
|---|-----|--------|
| 1 | **securitySchemes**: у нас `ApiKeyAuth` (query `access_token`) **и** `BearerAuth`; в оригинале — только `access_token` в query (устаревший способ авторизации). | Мы дополнительно описываем актуальную Bearer-авторизацию, которой реально пользуются современные боты. `scripts/compare.py` вообще не сравнивает `security`/`securitySchemes`, так что это не порождает ни `DIFF`, ни `KNOWN` — отличие фиксируется только здесь, в README. |
| 2 | Схема **`bigint`** оригинала не воспроизводится. | Это служебный алиас `{type: integer, format: int64}` — техническая деталь генератора оригинала, не самостоятельная сущность домена. Мы используем `int64` напрямую. Схема внесена в `NAME_ALLOW_MISSING` в `scripts/compare.py`, поэтому её отсутствие не считается пропущенной схемой. |
| 3 | **`uniqueItems`** (7 мест: `ChatMember.permissions`, `ChatAdmin.permissions`, `Subscription.update_types`, `SubscriptionRequestBody.update_types`, `UserIdsList.user_ids`, параметры `permissions` у `GET /chats/{chatId}/members` и `types` у `GET /updates`) и **`readOnly`** (1 значимое место — `User.name`; остальные 92 места в оригинале — явное `readOnly: false`, т.е. дефолт, не несущий смысла) не переносятся в TypeSpec. | В TypeSpec нет прямого аналога `uniqueItems` для массивов; `readOnly` на `User.name` — семантическая деталь, не влияющая на структуру запросов/ответов бота. `scripts/compare.py` не включает ни `uniqueItems`, ни `readOnly` в список сравниваемых `CONSTRAINTS`, поэтому это осознанно не проверяется (тихий пропуск, а не `KNOWN`-паттерн). |
| 4 | **`UserIdsList`** (тело `POST /chats/{chatId}/members`): в оригинале — параметро-подобная обёртка (вложенный `schema`, `style`, строковый `maxItems: "100"` на `items`); у нас — чистый `@maxItems(100) user_ids: int64[]`. | Оригинал скопировал форму OpenAPI-параметра внутрь тела запроса (артефакт генератора). Мы транскрибируем содержательный смысл ограничения. Схема UserIdsList эмитится и ссылается одинаково с обеих сторон; diff проявляется только на уровне requestBody, потому что $ref-пара впервые посещается при обходе paths.* (он идёт раньше цикла по components.schemas), и повторный визит гасится кэшем дедупликации compare.py. |
| 5 | **Дискриминаторы**: `ChatButton` (`"chat"`), `DataAttachment` (`"data"`), `ReplyKeyboardAttachment`/`ReplyKeyboardAttachmentRequest` (`"reply_keyboard"`), `MessageChatCreatedUpdate` (`"message_chat_created"`) — литералы отсутствуют в `discriminator.mapping` соответствующих базовых схем оригинала (`Button`, `Attachment`, `AttachmentRequest`, `Update`), хотя сами схемы-наследники присутствуют и структурно однозначно соответствуют этим ключам. | Недосмотр оригинала: mapping соседних дискриминаторов (`callback`, `link`, `photo`, `message_created` и т.д.) заполнен полностью, а эти четыре — пропущены. Значения литералов выведены по конвенции имени схемы и соседних ключей (**задокументировано как обоснованная догадка**, не как гарантированный факт из оригинала). Каждый случай — отдельный точечный regex в `DEVIATIONS` (`mapping[chat]`, `mapping[data]`, `mapping[reply_keyboard]`, `message_chat_created`). |
| 6 | **`ReplyButton`** (и его дочерние формы по `<mapping>`-цепочке компаратора) в оригинале **не объявляет** свойство `type` в `properties`, несмотря на то что `type` — поле дискриминатора `Button`. У нас `type` объявлен явно (как и у всех прочих наследников `Button`). | Непоследовательность оригинала: у всех остальных наследников `Button` поле дискриминатора объявлено. Мы эмитируем `type` единообразно — это корректно с точки зрения OpenAPI (поле дискриминатора обязано быть объявлено у каждого варианта). В 0.0.33 оригинал начал требовать `type` в `required`, по-прежнему не объявляя его в `properties`: половина отклонения закрылась, паттерн по `required` снят. |

Мы выбрали объектный вариант. | Подтверждается аналогией: `VideoAttachmentDetails.thumbnail` в том же оригинале типизирован как `PhotoAttachmentPayload` (объект), т.е. `type: "string"` у `VideoAttachment.thumbnail` — явный рудимент более ранней версии схемы, где миниатюра была просто URL-строкой. Заякорено regex по diff-сообщению `attachments[]...thumbnail: type: официально 'string'`, встречается и в `schemas.*`, и в `paths.*` (Task 9 — любая операция, возвращающая вложение, заново раскрывает `Attachment`). |
| 9 | **`Subscription.update_types`**: элементы массива в оригинале несут `minLength: 1` (непустая строка). Ограничение не переносится. | В TypeSpec ограничение на элементе (а не на самом массиве) строк выражается только через именованный scalar-тип (`@minLength(1) scalar X extends string`), который эмиттер `@typespec/openapi3` неизбежно материализует как отдельную схему в `components.schemas` — схему, которой нет в оригинале. Осознанно жертвуем точечным ограничением ради отсутствия постороннего артефакта в списке схем. ### Нормализации сверки (не отличия спецификации, а шум эмиттера/оригинала)

Эти правила зашиты в `constraints_of()` и `cmp_schema()` в `scripts/compare.py`
и не связаны с содержательными решениями о составе API — они компенсируют
несущественные различия между тем, как официальный генератор и
`@typespec/openapi3` оформляют одну и ту же семантику:

- **`type: "object"`** не сравнивается: `@typespec/openapi3` всегда проставляет
  его явно у объектных схем, оригинал — почти никогда.
- **`pattern`** на схемах с `type: "integer"` игнорируется — паттерн на числе
  не имеет смысла и является рудиментом оригинала.
- **`minLength`** на схеме с `type: "array"` трактуется как `minItems` (артефакт
  оригинала на некоторых массивах кнопок клавиатур).
- **`format: "string"`** на схеме с `type: "array"` отбрасывается (тот же
  артефакт, что у `message_ids`, см. п.11 выше, но за пределами
  задокументированного основного случая).
- Строковые числа (`"100"` вместо `100`) в ограничениях приводятся к `int`
  перед сравнением.
- **`enum`**-схемы без `type: "string"` в оригинале не считаются
  расхождением по `type`.
- Однозначный enum литерала дискриминатора (`{type: string, enum: [x]}` —
  то, во что компилируется `type: "x"` в TypeSpec на наследнике) сравнивается
  с нетипизированным строковым полем базовой схемы оригинала как
  эквивалент — но **только** для самого поля дискриминатора
  (`is_disc_prop`), чтобы случайный жёсткий enum на обычном свойстве не был
  случайно проглочен.
- **`style`/`explode`** у параметров не сравниваются: оригинал ставит
  невалидный для query `style: simple` на массивных query-параметрах, мы
  эмитим эквивалентный на проводе `explode: false`.
- **`tags`** сравниваются как подмножество: официальные теги обязаны
  присутствовать у нас, но допускаются дополнительные сквозные теги
  (например `bot-sending` — см. раздел «Роли методов»).
- **Две формы полиморфизма.** Оригинал описывает дискриминированный union
  парой «база-объект со свойствами + наследники через `allOf`», мы —
  канонической формой `oneOf` + `discriminator` (см. «Дискриминированные
  union'ы»). `compare.py` сопоставляет их как эквивалентные:
  - у базы не сравниваются `properties`/`required` — в нашей форме их у неё
    нет, они продублированы в каждом варианте и сверяются повариантно, где
    `flatten()` подмешивает свойства базы оригинала в её наследника. Потеря
    покрытия нулевая: пропажа любого свойства базы всплывёт на каждом из
    вариантов, а не один раз на базе;
  - у варианта не сравнивается `discriminator` — в форме оригинала он
    затекает в наследника через `allOf`, в нашей остаётся только на базе,
    где и сверяется;
  - взамен проверяется, что состав `oneOf` совпадает с `discriminator.mapping`.
    Вместе с обычной сверкой самого `mapping` это замыкает цепочку
    «наследники оригинала → его `mapping` → наш `mapping` → наш `oneOf`».

  Обе нормализации включаются только при виде `oneOf`; на нерасплющенной
  схеме сверка работает буква в букву как раньше (проверено: те же
  8 расхождений и 1518 известных отличий, ни одна из новых веток не
  срабатывает ни разу за 1718 сравнений схем).

## Требования КБ к схеме

Валидатор КБ читает каждую схему и каждое свойство изолированно и требует
трёх вещей:

1. у каждой схемы/свойства есть `description`;
2. у каждой схемы/свойства явно указан `type`;
3. у каждой схемы с `type: string` указан `pattern`.

Проверка воспроизведена в `scripts/validate_kb.py` (сверена с отчётом
валидатора: на пересекающемся диапазоне строк совпадение 50/50):

```bash
make validate     # либо: npm run validate
```

Как выполняются требования:

| Требование | Где выполняется | Как |
|---|---|---|
| `description` у свойства | `*.tsp` | doc-комментарий `/** … */` у каждого поля, включая литералы дискриминаторов (`type: "callback"` → «Тип кнопки: `callback`») |
| `type` у свойства | постобработка | пустые стабы `prop: {}` заменяются полным объявлением из базовой схемы — см. ниже |
| `pattern` у строк | `*.tsp` | инлайновый `@pattern` у каждого строкового поля |

**Происхождение лимитов — в `description`.** Пояснение к каждому
ограничению (`maxLength`/`minLength`/`maxItems`: откуда взято значение —
из официальной схемы, зеркалом какого официального лимита является или по
какой аналогии выбрано, если в оригинале лимита нет) живёт не в
`//`-комментарии рядом с декоратором, а последней фразой doc-комментария
поля — и потому попадает в `description` сгенерированного OpenAPI:

```tsp
/** Токен кнопки. 1024 — значение из официальной схемы MAX */
@maxLength(1024)
@pattern("^[\\w\\W]{0,1024}$")
payload: string;
```

`description`/`summary` сверкой не сравниваются (см. `scripts/compare.py`),
так что на число расхождений с оригиналом это не влияет. В `//`-комментариях
остаются только заметки, не относящиеся к контракту: TODO и объяснения
приёмов TypeSpec/эмиттера.

**Пустые стабы наследников.** При `seal-object-schemas: true` эмиттер обязан
перечислить у схемы-наследника все унаследованные свойства — иначе
`additionalProperties: false` отсекал бы их как посторонние. Перечисляет он их
пустыми схемами `prop: {}`: тип и ограничения приходят из базовой схемы через
`allOf`, что корректно по OpenAPI, но не проходит поизолированную проверку КБ.
`scripts/fill_inherited_stubs.py` подставляет вместо `{}` полное объявление,
найденное по цепочке `allOf` (рекурсивно, для многоуровневого наследования
`BotInfo` → `UserWithPhoto` → `User`). Ограничения при этом дублируются, а не
меняются: `allOf`-пересечение с идентичной копией эквивалентно исходной схеме,
поэтому сверка с оригиналом не даёт ни одного нового расхождения.

**Идиома `pattern`.** Там, где у поля нет содержательной структуры (свободный
текст, имена, описания, токены, URL, локали) используется
`^[\w\W]{minLength,maxLength}$` — `[\w\W]` есть объединение класса и его
дополнения, то есть любой символ, включая перевод строки. Паттерн выражает
ровно то же, что и соседний `maxLength`, и не сужает множество допустимых
значений. Это осознанный выбор: схема транскрибирует чужой сервер, реальное
множество значений (юникод в именах, произвольные CDN-URL, непрозрачные
токены) нам не подконтрольно, и слишком узкий алфавит отвергал бы валидные
ответы MAX. Содержательные паттерны остаются там, где формат известен точно:
`^[a-z_]+$` у типов вложений/событий/кнопок, `^https://.+$` у URL вебхука
в теле `POST /subscriptions`, `^[a-zA-Z0-9._\-]+$` у `mid`, base64-алфавит у
`videoToken`. У `url` в `DELETE /subscriptions` — намеренно «любая строка»:
в query значение приходит percent-encoded (`https%3A%2F%2F…`), и валидатор
периметра сверял его с `^https://` до декодирования, отвергая каждую отписку.

## Дискриминированные union'ы

Ещё два требования КБ — «не использовать `oneOf`/`anyOf`/`allOf` совместно с
другими ключами» и «у object-схемы должны быть явные свойства и
`additionalProperties: false`» — для полиморфных семейств закрывает
`scripts/flatten_discriminated_unions.py` (что остаётся без флага после него
и почему — ниже, «Где нет `additionalProperties: false`»). Он переписывает полиморфное
семейство из формы, в которую TypeSpec-наследование переводит эмиттер, в
каноническую для OpenAPI:

```yaml
# БЫЛО
Update:            {type: object, properties, required, discriminator, description}
BotStartedUpdate:  {type: object, properties, required, additionalProperties: false,
                    allOf: [$ref Update], description}

# СТАЛО
Update:            {oneOf: [...16 ссылок], discriminator, description}
BotStartedUpdate:  {type: object, properties, required: <свой + базы>,
                    additionalProperties: false, description}
```

Расплющиваются все шесть дискриминаторных семейств: `Update` (16 вариантов),
`Attachment` (11), `AttachmentRequest` (10), `MarkupElement` (10), `Button`
(8), `ReplyButton` (3) — 58 вариантов в `MaxBotApi`, 48 в `MaxBotWebhook`
(там нет `AttachmentRequest`).

**Файл при этом становится короче**, а не длиннее (−100 и −82 строки):
`fill_inherited_stubs.py` уже вкопировал в каждого наследника полные
объявления унаследованных свойств, поэтому удаление `allOf` — чистый минус.
Единственное, чего в наследниках не хватало, — `required` базы (эмиттер не
дублирует его, полагаясь на пересечение через `allOf`); его дописывает
скрипт. Композитных схем становится 71 вместо 123 в `MaxBotApi` и 58 вместо
101 в `MaxBotWebhook`.

**Это не косметика, а починка дыры в валидации.** `kin-openapi` (и не он
один) не использует `discriminator` голой object-схемы, чтобы перейти к
конкретному варианту, — а против базы валидируются именно полиморфные поля
(`updates: Update[]`, `attachments: AttachmentRequest[]`). Проверялись только
свойства самой базы, у `Attachment` это один `type`. Замерено на
`maxmoc/cmd/validate-capture`:

| Тело `NewMessageBody` | до | после |
|---|---|---|
| вложение `location` с `latitude: 991` (вне −90..90) | **valid** | invalid |
| вложение `location` с полем вне контракта | **valid** | invalid |
| кнопка `callback` с `text` длиннее 128 | **valid** | invalid |

То есть ограничения, навешенные на конкретные варианты, для полиморфных полей
до этого просто не работали. Первый же прогон тестов `maxmoc` на расплющенной
схеме нашёл этим настоящий дефект мока: `photo_id` генерировался 63-битным
хэшем, вне объявленной контрактом JSON-безопасной границы `2^53−1`.

### Что остаётся композитным — и почему это потолок

| Что | `MaxBotApi` | `MaxBotWebhook` | Можно ли убрать |
|---|---:|---:|---|
| `allOf: [$ref]` + `description` — ссылка с описанием | 47 | 39 | нет, см. ниже |
| `allOf: [$ref]` + `nullable`/`description` | 13 | 9 | нет: `nullable` рядом с `$ref` — это семантика, а не оформление; `type: object`, который ставил рядом эмиттер, снят (см. «Где нет `additionalProperties: false`») |
| `allOf: [$ref]` + свои `properties` — обычное наследование | 0 | 0 | убрано: поля базы вписаны spread'ом (ниже) |
| `oneOf` + `discriminator` + `description` — базы | 6 | 7 | это и есть целевая форма |
| `anyOf` без соседних ключей — тело вебхука | — | 1 | можно, но это решение по продукту, а не требование формата (ниже) |
| **Итого** | **66** | **55** | |

Для сравнения: официальная схема MAX содержит **125** композитных узлов, из
них **110** с посторонними ключами — в том числе 54 узла настоящего
`allOf`-наследования, которого у нас теперь не осталось вовсе. По этому
требованию наш документ уже чище оригинала.

**Про `allOf: [$ref]` + `description` (86 узлов, две трети остатка).** В
OpenAPI 3.0 `$ref` рядом с другими ключами игнорируется, поэтому одиночную
ссылку приходится заворачивать в `allOf`, если рядом нужно описание. Два
очевидных обходных пути проверены и отвергнуты — оба замером, а не
рассуждением:

- **Написать `{$ref, description}` без обёртки.** Композитных узлов стало бы
  44 вместо 130 — самый крупный выигрыш из возможных. Но `kin-openapi`
  отказывается загружать такой документ целиком:
  `invalid oneOf element: extra sibling fields: [description]`. Это не
  предупреждение, а ошибка на старте — `maxmoc` просто не поднялся бы. Тот же
  запрет у Spectral (`no-$ref-siblings`, ошибка для 3.0).
- **Перейти на OpenAPI 3.1**, где соседи у `$ref` легальны. Проверено
  экспериментом (`openapi-versions: ["3.1.0"]`): становится **хуже** — 206
  композитных узлов вместо 130 в сыром выводе эмиттера. Во-первых,
  `@typespec/openapi3` и в режиме 3.1 продолжает заворачивать `$ref` +
  `description` в `allOf`, то есть возможностью 3.1 не пользуется.
  Во-вторых, `nullable: true` в 3.1 не существует, и каждое nullable-поле
  превращается в `anyOf: [{type: x}, {type: 'null'}]` — это плюс 87 новых
  композитных узлов там, где раньше был обычный ключ.

**Про обычное наследование (было 9 узлов, теперь 0).** Раньше его оставляли:
выигрыш в шесть узлов не окупал потерю схемы `AttachmentPayload`, которая
после расплющивания становится недостижимой. Решило дело не требование КБ, а
валидатор периметра. Atlassian `swagger-request-validator` по умолчанию сам
дописывает `additionalProperties: false` в каждую схему с `properties`, где
флаг не задан, — и ветвь `allOf` базы начинает отвергать поля наследника. На
живом MAX так падали стикеры (`code` отвергала база `AttachmentPayload`) и
`GET /me` (`commands` отвергали `User` и `UserWithPhoto`), а по построению —
каждое вложение `file`, `audio` и `video`. Отключить подстановку можно только
настройкой валидатора, и тогда он перестаёт проверять лишние поля совсем.

Поэтому наследники вписывают поля базы spread'ом прямо в TypeSpec
(`...User` вместо `extends User`): эмиттер выдаёт плоскую схему с полным
набором свойств, без `allOf` и без участия `fill_inherited_stubs.py`, так что
прежняя опасность потерять свойства `UserWithPhoto` не возникает. Базы
`User` и `UserWithPhoto` при этом тоже запечатаны — наследниками их больше
никто не расширяет. Цена — `AttachmentPayload`, вырезанная как недостижимая
(см. п. 16 таблицы отличий).

**Про `anyOf` тела вебхука (1 узел).** Единственный композитный узел без
посторонних ключей — то есть требование КБ он не нарушает, и «убрать» его
формат не требует. Но убрать его **можно**: это `@body update: UpdateUnified
| WebhookUpdate` в `webhook.tsp`, то есть сознательное предложение двух форм
на выбор разработчика бота (см. «Как реализовать webhook-сервер»). Оставить
одну — решение по продукту: уйдёт либо плоская схема в стиле Telegram, либо
типизированная кодогенерация.

У этого узла есть цена, которую стоит знать: `anyOf` проходит при совпадении
**хотя бы одной** ветви, а `UpdateUnified` требует всего `update_type` и
`timestamp`. Значит для валидатора, который сверяет тело с операцией, 37
обязательных полей 16 типов событий становятся необязательными: проходят
`message_created` без `message`, `user_added` без `chat_id`, событие с
неизвестным `update_type` и даже смесь полей от разных вариантов. Это ровно
та же дыра, что закрыло расплющивание, только уровнем выше. Потребителю,
который на контракте проверяет **свои исходящие** события, нужно сверяться
напрямую со схемой `WebhookUpdate`, а не с телом операции — так теперь и
делает `maxmoc` (см. `ValidateWebhookBody` и раздел «Соответствие контракту»
в его README).

Вывод: **66 и 55 — это пол для OpenAPI 3.0 с этим эмиттером**, а не
недоделка.

Всё перечисленное продублировано в самих документах:
`scripts/annotate_composites.py` ставит у каждой композитной позиции
однострочный комментарий с буквой случая и причиной, а в начало файла —
блок с разбором и подсчётом. Там же у каждого случая пометка «В ОРИГИНАЛЕ» с
конкретными схемами MAX, которые записаны так же: `Chat.type` и
`Message.sender` для `allOf` вокруг `$ref`, `Chat.icon` и
`Chat.pinned_message` для того же с `nullable`, те же шесть дискриминаторов
для полиморфных полей. Читающему
YAML не нужно держать этот README перед глазами; на потребителей документа
комментарии не влияют.

`WebhookUpdate` (в `openapi.MaxBotWebhook.yaml`) приходит в форме `oneOf`
прямо из TypeSpec — это `union` с `@discriminated`, и `discriminator` с
полным `mapping` у него теперь тоже есть. Без него `kin-openapi` перебирал
все 16 ветвей и выдавал бесполезное `doesn't match any schema from "anyOf"`,
не называя виноватое поле; с ним диагностика указывает конкретный вариант.
Скрипт снимает у него единственный лишний ключ — `type: object`, который
эмиттер проставляет рядом с `oneOf`.

### Где нет `additionalProperties: false` — и почему

Требование КБ [59] — «явные свойства и `additionalProperties: false` у каждой
object-схемы». Эмиттер (`seal-object-schemas: true`) ставит флаг всем
object-схемам, кроме тех, где он сломал бы семантику; после сборки таких
остаётся 2 в `MaxBotApi` и 1 в `MaxBotWebhook` — только словари.

| Что | `MaxBotApi` | `MaxBotWebhook` | Почему нельзя |
|---|---:|---:|---|
| `{type: object, additionalProperties: {$ref}}` — словарь (`Chat.participants`, `PhotoAttachmentRequestPayload.photos`) | 2 | 1 | ключи динамические (`user_id → время активности`), в `properties` их не перечислить, `patternProperties` в OpenAPI 3.0 нет; `additionalProperties` здесь — схема значений, `false` сделал бы словарь всегда пустым. В оригинале записано так же |

**Nullable-обёртки `{allOf: [$ref], nullable: true}`** (`Chat.icon`,
`Chat.pinned_message`, `CallbackAnswer.message`; 12 позиций в `MaxBotApi` и 9
в `MaxBotWebhook`) в эту таблицу не попадают. Эмиттер ставил им `type: object`
для `Model | null`, потому что по OAS 3.0.3 `nullable` действует только рядом
с явным `type`, и правило [59] срабатывало именно на него. Поставить флаг на
обёртку нельзя: своих `properties` у неё нет, `false` отверг бы все поля
целевой схемы, и поле принимало бы только `{}` и `null`. Поэтому
`scripts/strip_nullable_wrapper_type.py` снимает `type: object` — это форма
самого оригинала MAX (16 из 19 таких обёрток там записаны без `type`).
Решение проверено замером:

| Кто читает контракт | С `type: object` | Без него |
|---|---|---|
| Go-модели `oapi-codegen` | | совпадают байт в байт |
| переходник `openapi_to_jsonschema.py` для quicktype | понимает | понимает, случай предусмотрен |
| `kin-openapi` (на нём `maxmoc`) | `null` проходит | `null` проходит |
| `openapi-schema-validator` (Python, строго по стандарту) | `null` отвергает | `null` отвергает |
| AJV (JS, строго по стандарту) | `null` отвергает | схему не компилирует: `"nullable" cannot be used without "type"` |
| Atlassian `swagger-request-validator` 2.46 (Java, валидатор периметра) | `null` отвергает | `null` отвергает |

Две вещи из этого замера стоит знать. Строгие по букве стандарта валидаторы
`null` через такую обёртку не пропускают ни с `type`, ни без: мешает ветвь
`allOf`, которой `null` не подходит; это свойство формы оригинала, не наше
(в официальной спецификации на GitHub форма та же). Таков и валидатор
периметра — Atlassian `swagger-request-validator`: `"link": null` в теле
`POST /messages` он отвергает сообщением `Instance failed to match all required
schemas (matched only 0 out of 1)`. Поэтому в теле запроса поля-обёртки
необязательны, и клиент опускает их, а не шлёт `null` (генераторы дают
`omitempty`); `kin-openapi` в `maxmoc` `null` пропускает и эту разницу не
ловит. И цена снятия —
несовместимость с AJV-валидаторами; если такой появится на пути контракта,
шаг `strip_nullable_wrapper_type.py` достаточно убрать из `Makefile`.

Баз `allOf`-наследования, которые раньше стояли в этой таблице (`User`,
`UserWithPhoto`, `AttachmentPayload`), больше нет: наследование вписано
spread'ом (см. «Про обычное наследование»), и `User` с `UserWithPhoto`
запечатаны как обычные схемы. Заодно закрылась прежняя оговорка: поля,
объявленные типом базы (`Message.sender: User`), теперь тоже отвергают
посторонние ключи.

Одну дыру закрыли по дороге: `SimpleQueryResult` оставался без флага только
потому, что эмиттер считал его базой для `ModifyMembersResult` — схемы из
выключенных маршрутов `/chats`, которую `prune_unused_schemas.py` затем
вырезает как недостижимую. Теперь чистка сама запечатывает такие осиротевшие
базы (если у них нет собственного `allOf`).

В официальной схеме MAX флага нет ни у одной из 129 схем. В документах всё
это продублировано: `annotate_composites.py` ставит у каждой такой схемы
строку `# незапечатано [буква] причина`, а после шапки про композиты — вторую
шапку с разбором по случаям. Позиция без опознанной причины помечается `[?]`
и выводится в лог сборки — это сигнал, что флаг забыт, а не запрещён.

Сверка с официальной схемой показывает **8 расхождений**, и все восемь —

сравниваются дважды — на ней самой и на каждом её варианте. Наглядно на
`ReplyButton.payload` (3 варианта):

```
# БЫЛО — 4 строки: сама база + каждый вариант
schemas.ReplyButton.payload:                                        pattern: … у нас '^[\w\W]{0,1024}$'
schemas.ReplyButton<message>.payload:                               pattern: … у нас '^[\w\W]{0,1024}$'
schemas.ReplyButton<message><user_contact>.payload:                 pattern: … у нас '^[\w\W]{0,1024}$'
schemas.ReplyButton<message><user_contact><user_geo_location>.payload: pattern: … у нас '^[\w\W]{0,1024}$'

# СТАЛО — 3 строки: только варианты
schemas.ReplyButton<message>.payload:            pattern: … у нас '^[\w\W]{0,1024}$'
schemas.ReplyButton<user_contact>.payload:       pattern: … у нас '^[\w\W]{0,1024}$'
schemas.ReplyButton<user_geo_location>.payload:  pattern: … у нас '^[\w\W]{0,1024}$'
```

Заодно распрямились пути: вариант больше не разворачивает `mapping` базы
заново, поэтому вместо накапливающейся цепочки `<a><b><c>` печатается просто
`<c>`. Набор проверяемых вариантов тот же. Ни один паттерн `DEVIATIONS` не
перестал срабатывать: не срабатывают те же три, что и раньше, — все они
обслуживают выключенные маршруты `/chats`.

Расхождение по `User.username` (было 35 строк) закрыто как осознанное
отличие: регресс на живом MAX показал, что из 27 снятых объектов `User` 22
приходят **без этого поля вовсе** — оно есть только у самого бота. Требование
оригинала отвергало бы каждое сообщение от человека без username.

Возврат `/chats` в сборку требует отдельного решения и здесь
намеренно не трогались.
