# max-mock

Stateful-эмулятор бот-платформы **Max** для закрытого контура: принимает
запросы КЦ-платформы по Bot API, доставляет webhook-события на стенды и даёт
тестировщику веб-чат, чтобы играть роль клиента мессенджера.

Источник правды о контракте — OpenAPI-артефакты из репозитория
[`maxapi`](../maxapi), лежащие в `api/` (версия контракта **0.0.33**).

## Быстрый старт

Нужен только Go ≥ 1.22 — ни npm, ни Docker, ни системного SQLite.

```bash
make run
```

Открыть **http://localhost:8080/mock** — админка: зарегистрировать бота и
получить `access_token`. Оттуда же — переход в веб-чат бота
(`/mock/chat/{botId}`), где тестировщик играет роль клиента.

Проверить всё разом на живом сервисе:

```bash
make smoke      # curl-сценарий: бот → подписка → диалог → кнопки → вложение
```

Перенос в закрытый контур — один статический файл:

```bash
make release    # max-mock-linux-amd64, ~13 МБ, без cgo и внешних зависимостей
```

**Подробная инструкция по запуску, настройке, работе в контуре и разбору
неполадок — [docs/run.md](docs/run.md).**

## Что умеет

| Операция Bot API | Поведение |
|---|---|
| `GET /me` | информация о боте, чей токен предъявлен, вместе со списком команд |
| `PATCH /me/commands` | публикация команд бота; пустой список удаляет все, отсутствие поля ничего не меняет |
| `GET /messages` | переписка диалога с фильтрами `chat_id`, `message_ids`, `from`, `to`, `count` |
| `POST /messages` | отправка сообщения (текст, инлайн-клавиатура, вложения) |
| `PUT /messages` | правка собственного сообщения бота |
| `DELETE /messages` | удаление собственного сообщения бота |
| `GET /messages/{messageId}` | сообщение по `mid` |
| `POST /answers` | ответ на нажатие кнопки, с опциональной заменой сообщения |
| `GET,POST,DELETE /subscriptions` | webhook-подписки бота |
| `POST /uploads` | адрес двухфазной загрузки медиафайла |

Исходящие события: `message_created`, `message_callback`, `message_edited`,
`message_removed`, `bot_started`, `bot_stopped`.

`message_created` и `message_edited` уходят по webhook только на действия
клиента: собственные сообщения бота и собственные его правки — в том числе
замена сообщения через `POST /answers` — ему не возвращаются, как и в живом
Max (замерено, см. [«Форма события, сверенная с продом»](#форма-события-сверенная-с-продом)).
Иначе любой бот, отвечающий на сообщения, зациклился бы на собственном эхо.
Веб-чат при этом видит обе стороны разговора: событие в UI публикуется всегда.

Действия тестировщика в веб-чате: создать клиента, нажать «Начать»/«Остановить»,
написать боту или выбрать команду из его меню, прикрепить файл, нажать
инлайн-кнопку, отредактировать и удалить своё сообщение. Всё обновляется
вживую по WebSocket, и каждое действие журналируется — см. «Лента диалога»
ниже.

Кнопка «Начать»/«Остановить» не одноразовая: подпись и состояние диалога
берутся из ответа сервера, а не запоминаются на клиенте, поэтому кнопка не
пропадает после первого нажатия. Так проверяется и повторный старт после
остановки — контракт называет это «начнёт **или возобновит** общение с
ботом».

Меню команд — полоса чипов над полем ввода, наполняется списком, который бот
опубликовал через `PATCH /me/commands`; пустой список команд прячет полосу
целиком. Клик по чипу шлёт обычное текстовое сообщение `/name`
(`message_created`), а не `bot_started`: в живом Max выбор команды из меню и
нажатие «Начать» — разные действия с разными событиями, и мок их не
смешивает.

Лента диалога (вкладка «События») показывает разговор мока и бота парами
«запрос → ответ», новые сверху. Карточка **«max → бот»** — событие, ушедшее на
стенд, и то, чем стенд ответил; карточка **«бот → max»** — вызов Bot API и
ответ мока. В обеих видны оба тела целиком; длинное свёрнуто до восемнадцати
строк с кнопкой «развернуть».

Тело ответа стенда сохраняется с потолком 8 КиБ: упавший стенд отвечает
HTML-страницей ошибки, и без ограничения она осела бы в базе на каждой попытке
каждого события. Обрыв связи на чтении тела не отменяет уже полученный статус
и не вызывает повтора: стенд событие принял, и повтор его продублировал бы.

В ленте только этот диалог. Вызовы бота вне диалога (`GET /me`, `PATCH
/me/commands`, подписки, загрузки) относятся ко всему боту и живут на вкладке
«Журнал». Действий тестировщика в ленте нет — он совершил их сам, а отказ
увидел алертом в момент клика; в журнале `ui_actions` они по-прежнему пишутся.

Событие, на тип которого стенд не подписан, видно карточкой «событие не
отправлено»: вместо кода — «нет ответа», а причина написана прямо, «нет
подписки на этот тип события», — не тишина, которая выглядит как «мок не
отправил».

В списке слева новые клиенты сверху. Выбранный диалог виден в адресе —
`/mock/chat/{botId}?chat={chatId}`: перезагрузка страницы и ссылка коллеге
открывают тот же чат. Если такого чата у бота нет, откроется первый в списке.

## Адреса и авторизация

Поверхность Bot API живёт **в корне**, путь в путь по документации Max:
`/me`, `/messages`, `/messages/{messageId}`, `/answers`, `/subscriptions`,
`/uploads`. Переезд приложения с прода на мок — это замена базового адреса
`https://platform-api2.max.ru` на адрес мока, и больше ничего.

Префикс `/mock` (админка, веб-чат, control-API, приём файлов, WebSocket) —
служебный интерфейс самого эмулятора. Приложение к нему не обращается; префикс
выбран так, чтобы ни один служебный путь не мог столкнуться с путём Max.

Авторизация — голый токен в заголовке, как на живом Max:

```
Authorization: <access_token>
```

Ни схема `Bearer`, ни query-параметр `access_token` не принимаются, хотя
контракт объявляет обе: живой API отвергает и то, и другое. Замеры и
обоснование — в разделе [«Контракт против живого API»](#контракт-против-живого-api).

## Модель ошибок

Тело ошибки всегда соответствует схеме `Error`: `{"code": "...", "message": "..."}`.

Официальный контракт Max описывает только `401`, `403`, `404` и `405`, поэтому
всё, что мок различает сверх контракта, помечено префиксом `mock.` — видно, что
это конвенция эмулятора, а не знание о проде:

| Код | Когда |
|---|---|
| `mock.validation` | запрос не прошёл валидацию по OpenAPI |
| `mock.not_implemented` | путь или операция вне объёма мока |
| `mock.chat.not_found` | неизвестный `chat_id` / `user_id` |
| `mock.message.not_found` | неизвестное или удалённое сообщение |
| `mock.callback.not_found` | неизвестный `callback_id` |
| `mock.attachment.not_found` | вложение не загружено |
| `mock.forbidden` | бот пытается тронуть чужое сообщение |
| `mock.internal` | ответ самого мока разошёлся с контрактом |
| `mock.conflict` | клиент с таким `user_id` уже есть |
| `verify.token` | нет токена, токен неизвестен или передан не так, как ждёт Max |

Последняя строка — единственный код без префикса `mock.`, и это намеренно: и
код, и англоязычные тексты его сообщений (`No access token`,
`Malformed access token`, `Invalid access_token`) дословно скопированы с
живого Max. Клиент вправе завязаться на них, и мок обязан отдать те же самые.

**Статус выбирается по контракту операции.** Если он в ней объявлен —
используется он (`GET /messages/{messageId}` на неизвестном `mid` → `404`).
Если нет — тот же код отдаётся с `400` (`DELETE /messages` → `400`
`mock.message.not_found`). Мок не выдумывает статусов, которых нет в спеке.

## Соответствие контракту

Кодогенерация не применяется: в спеке `text`/`attachments`/`link` объявлены
одновременно обязательными и nullable, а вложения и кнопки — дискриминируемые
объединения. Генератор превращает это в union-типы, где различие «поле `null`»
и «поля нет» приходится восстанавливать руками, — а именно оно отличает
корректный `PUT /messages` от некорректного. Вместо этого структуры написаны
явно (`internal/wire`), а соответствие проверяется на реальных байтах на трёх
рубежах:

1. **Входящий запрос** — против `api/openapi.MaxBotApi.yaml`; не прошёл →
   `400 mock.validation`.
2. **Исходящий ответ** — против того же контракта (`validate_responses`, по
   умолчанию включено); не прошёл → `500 mock.internal` и запись в журнал.
   Это ловит ошибку мока до того, как её увидит КЦ.
3. **Исходящее событие** — против `api/openapi.MaxBotWebhook.yaml` перед
   отправкой; не прошло → на стенд не уходит, в журнале доставок появляется
   отказ. Проверка идёт **по строгой ветви** контракта (`WebhookUpdate`), а
   не только по операции: тело операции описано как
   `anyOf: [UpdateUnified, WebhookUpdate]` — две равноправные формы на выбор
   разработчика бота, и плоская `UpdateUnified` требует лишь `update_type` и
   `timestamp`. `anyOf` проходит при совпадении хотя бы одной ветви, так что
   без отдельной сверки через неё пролезали бы `message_created` без
   `message`, `user_added` без `chat_id`, событие с неизвестным
   `update_type` и даже смесь полей от разных вариантов — 37 обязательных
   полей на 16 типов событий. Мок события порождает, а не принимает, и обязан
   держать себя строже, чем контракт разрешает приёмнику.

Поверх — сквозные тесты `e2e/`, проходящие полный сценарий интеграции и
проверяющие обе стороны обмена по контракту:

```bash
make e2e
```

**Полиморфные поля проверяются целиком.** До перевода контракта в форму
`oneOf` + `discriminator` (см. «Дискриминированные union'ы» в
`../maxapi/README.md`) `kin-openapi` не переходил от базовой схемы к
конкретному варианту: у `attachments`, `updates`, `buttons` проверялось
только поле-дискриминатор, а все ограничения самих вариантов —
`additionalProperties`, длины, границы чисел — не работали вовсе. Первый же
прогон на новой форме нашёл этим настоящий дефект мока: `photo_id`
выводился 63-битным хэшем токена, вне объявленной контрактом JSON-безопасной
границы `2^53−1` (см. `ids.maxSafeID` — та же причина, по которой в этом
диапазоне держатся `chat_id` и `user_id`).

### Две компенсации дефектов артефакта

Загрузчик спеков (`internal/specs`) правит два места по вине самого артефакта;
каждая правка задокументирована в коде с обоснованием:

- `BearerAuth.scheme` приводится к нижнему регистру — реестр HTTP
  Authentication Schemes (RFC 7235) содержит имена строчными.
- `pattern` компилируется движком с поддержкой ECMAScript: `callback_id`
  объявлен через опережающую проверку `^(?!\s*$).+`, которой нет в RE2.

Третья правка — `ChatType` дополнялся значением `dialog` — снята в 0.0.33:
контракт больше не объявляет `ChatType` закрытым перечислением (`enum` из
одного `"chat"` при описании «Тип чата: диалог, чат» отвергал каждое
сообщение диалога). Теперь это строка с ограничениями по форме, и
компенсировать нечего.

### Послабление ради контура: подписка на `http://`

Третья правка загрузчика — не починка артефакта, а сознательное отступление.
`SubscriptionRequestBody.url` объявлен как `^https://.+$`; загрузчик заменяет
паттерн на `^https?://.+$`.

Здесь контракт прав: живой Max требует HTTPS, а паттерн лишь переносит это
требование из описания поля в проверяемую форму (в официальной схеме его нет,
добавлен в `maxapi` 0.0.33). Но мок ставят в закрытый контур, где стенды КЦ
живут на открытом HTTP, а выпустить им сертификат зачастую негде и некому, —
отвергая такую подписку, мок становится в контуре неприменим, ради которого и
сделан.

Послабление минимальное: необязательной становится только буква `s`, проверка
формы остаётся — `ftp://`, «адрес стенда» без схемы и голое `https://`
отвергаются по-прежнему. Принятую http-подписку мок помечает в поле `message`
ответа, чтобы отступление видел вызывающий, а не только читатель этого файла.

`url` в `DELETE /subscriptions` контракт объявляет «любой строкой»
(`^[\w\W]{1,2048}$`): в query значение приходит percent-encoded
(`https%3A%2F%2F…`), и валидатор периметра сверял его с `^https://` до
декодирования, отвергая каждую отписку. Поэтому отписку загрузчик не правит,
а сверяет: если шаблон снова ужесточат, мок падает на старте — иначе
http-подписку, которую снимает при старте бот, переехавший на новый адрес,
стало бы нельзя снять.

Ужесточение паттерна в 0.0.33 это послабление однажды уже отменило: ветка,
помечавшая http-подписку, стала недостижимой и была удалена как мёртвая, а
`maxbotdemo` перестал подниматься против мока по инструкции из собственного
README. Поэтому загрузчик теперь сверяет исходный паттерн и падает на старте,
если контракт переписали: молчаливое «правка ни к чему не применилась» —
ровно тот отказ, который тогда никто не заметил.

### Контракт против живого API

Правки-компенсации выше чинят спеку по её же смыслу: она противоречила сама
себе.
С авторизацией случай другой — спека внутренне непротиворечива, она просто
отстала от API. Замер `GET /me` на проде токеном рабочего бота (2026-08-06):

| Форма | Живой Max | Что объявляет контракт |
|---|---|---|
| `Authorization: <token>` | `200` | не объявлена |
| `Authorization: Bearer <token>` | `401` | `BearerAuth` |
| `?access_token=<token>` | `401` | `ApiKeyAuth` |

Документация Max говорит то же: «Передача токена через query-параметры больше
не поддерживается — используйте заголовок `Authorization: <token>`».

Мок выбирает измеренное поведение прода, потому что его назначение — заменить
прод, а не контракт. Артефакт `api/openapi.MaxBotApi.yaml` при этом почти не
правится: он принадлежит [`maxapi`](../maxapi) и переписан с официальной схемы
Max, где `BearerAuth` нет вовсе, а `access_token` в query объявлен.
Единственная нанесённая правка — `username` (см. ниже); она помечена в обоих
YAML комментарием «ПРАВКА МОКА» и требует повторного нанесения при обновлении
спеки с апстрима.

Поведение измерено, а не выведено, — значит, может измениться. Скрипт для
повторного замера лежит в `docs/specs/2026-08-06-auth-parity-tz.md`; если
эталон разойдётся с таблицей приёмки оттуда, правится мок, а не таблица.

### Форма события, сверенная с продом

Второй замер (2026-08-07): запись `message_created` с живого Max — ответ
пользователя на кнопку `request_contact`. Мок расходился с ней по девяти
пунктам; образец и проверки лежат в `internal/core/live_sample_test.go`.

| Поле | Живой Max | Было в моке |
|---|---|---|
| `body.seq` | `117052520019991875` | `25` |
| `body.mid` | 32 hex | 24 hex |
| `body.text` (сообщение из одних вложений) | `""` | `null` |
| `sender.username` (нет публичного имени) | поля нет | `null` |
| `sender.last_name` (нет фамилии) | `""` | поля нет |
| `sender.last_activity_time` у пользователя | до секунды (`…712000`) | до миллисекунды |
| `timestamp` события и сообщения | совпадают | расходились |
| `contact.hash` | 64 hex | 32 hex |
| `contact.vcf_info` | `PRODID`, `TEL` до `FN`, `TYPE=cell`, номер из цифр | без `PRODID`, `FN` до `TEL`, `TYPE=CELL`, номер как введён |

Главный из них — `seq`. Он оказался не счётчиком, а упакованным временем:
`seq >> 16` даёт ровно `timestamp` сообщения, младшие 16 бит — счётчик внутри
миллисекунды. Значение выходит за `Number.MAX_SAFE_INTEGER`, то есть в
JavaScript теряет точность. Мок с маленьким счётчиком молча пропускал бы
клиента, который на проде получит искажённый номер, поэтому формат
воспроизведён точно — включая ненулевой счётчик, без которого `время << 16`
проходит через `float64` без потерь. Идентификаторы чатов и пользователей,
наоборот, держатся внутри безопасной зоны: там прод выдаёт значения на
порядки меньше (см. `internal/ids/ids.go`).

`username` — единственный пункт, ради которого пришлось тронуть спеку: она
объявляет поле обязательным, то есть прод нарушает собственный контракт.
Оставить `null` значило бы скрыть от клиента, чья модель сгенерирована из
спеки, что на проде он упадёт; поэтому поле убрано из `required` в обоих
YAML — иначе диспетчер отвергал бы собственные события мока.

Третий замер (текстовое сообщение и ответ бота на него) подтвердил формат
`seq` ещё на двух продовых записях и уточнил одно: `last_activity_time`
округляется до секунды **только у пользователя**. У бота прод отдаёт его с
миллисекундами (`1786081137409` при timestamp сообщения `1786081137396`) —
похоже, у пользователя это отдельно хранимое «был в сети», а у бота просто
текущее время.

Четвёртый замер (клавиатура из четырёх рядов) дал ещё одно: в теле
возвращённого сообщения прод достраивает у кнопки `request_geo_location`
умолчание `"quick": false`, хотя в запросе поля не было. Контракт объявляет
его через `default`, и это единственное умолчание среди кнопок — у остальных
типов поля `quick` в схеме нет. Мок достраивает его так же.

Пятый замер (нажатие кнопки) дал два: `callback_id` у прода — 116 символов
base64url без префикса (образец декодируется ровно в 87 байт), а у мока был
`cb.<32 hex>`, втрое короче; и `timestamp` события `message_callback`
совпадает с `timestamp` самого нажатия, как и в `message_created`. Длина
`callback_id` — та же ловушка, что и `seq`: клиент с короткой колонкой под
идентификатор на моке проходил бы, а на проде терял ответ на нажатие.
Контракт длину не ограничивает (`callback_id` объявлен как непустая строка),
так что правки спеки здесь не потребовалось.

Шестой замер (нажатие с логом, продолженным после ответа) закрыл вопрос,
который до него был открыт: **на правку, сделанную самим ботом, живой Max
события не присылает**. После `POST /answers`, заменившего текст сообщения,
пришёл только `200 {"success":true}`. Контракт говорит то же: «Вы получите
это событие, как только *пользователь* отредактирует сообщение». Мок раньше
слал `message_edited` и на такие правки — теперь не шлёт ни на ответ по
кнопке, ни на `PUT /messages`; правка клиента доставляется по-прежнему.

В том же образце видно, что `callback_id` не полностью случаен: у двух
нажатий совпали первые 8 байт (`7fd2c7a1d0f470e2`), дальше 79 различаются.
Оба нажатия сделаны одним пользователем в одном диалоге, поэтому к чему
привязан префикс — к боту, к диалогу или к установке — по этим данным не
определить. Мок генерирует все 87 байт случайными: воспроизводить структуру,
не зная её области действия, значило бы выдумывать. Замер, который это
закроет, — нажатие кнопки в другом диалоге того же бота.

Два расхождения оставлены намеренно. Порядок ключей в JSON (`update_type` у
прода в конце, у мока в начале) ничего не значит для разбора. Разрядность
`chat_id` и `user_id` (у прода 9 знаков, у мока 16) — сознательная строгость
мока: она ловит клиентов, которые кладут идентификатор в 32-битное поле, а
прод такого клиента пропустил бы.

### Заголовки доставки, сверенные с продом

Третий замер (2026-09-29): заголовки вебхуков живого MAX, пять событий трёх
типов (`message_created`, `bot_stopped`, `bot_started`). От самого MAX их
четыре, у всех событий одинаковые:

| Заголовок | Живой MAX | Мок |
|---|---|---|
| `User-Agent` | `OneMe/0.1.10 Bot API` | тот же; до замера — `Go-http-client/1.1` |
| `X-Max-Bot-Api-Secret` | в каждом запросе, если подписка создана с `secret` | так же; без `secret` заголовка нет (`TestNoSecretHeaderWhenNotConfigured`) |
| `Content-Type` | `application/json; charset=UTF-8` | `application/json` |
| `Content-Length` | размер тела | так же |

Своих заголовков с адресом отправителя MAX не шлёт; адрес видно только по
соединению (в замере через туннель — по `Cf-Connecting-Ip`, который ставит
Cloudflare): пул VK, `31.177.104.0/22` и `89.221.228.0/22`.

### Токену reply-кнопки некуда ехать

Контракт описывает две разные кнопки с типом `message`: inline
`MessageButton` наследует `Button`, где есть только `text`, а
reply-клавиатурная `SendMessageButton` наследует `ReplyButton`, где объявлен
`payload` с описанием «Токен кнопки». Но `MessageBody` — тело, в котором
событие `message_created` приезжает на стенд, — полей под этот payload не
имеет вовсе.

Следствие для КЦ: **нажатие `message`-кнопки неотличимо от того, что
пользователь набрал ту же строку руками**, ни у inline-, ни у
reply-клавиатуры. Нужна различимость — используйте `callback` с `payload`.

Мок воспроизводит контракт: шлёт обычное `message_created` с текстом кнопки и
ничего не выдумывает. В отличие от авторизации, это расхождение на живом Max
**не измерялось** — утверждать, что прод ведёт себя так же, нельзя.

### Остановка не запрещает боту писать

`bot_stopped` — новое событие, и контракт описывает только сам факт остановки
(`chat_id`, `user`), а не то, что происходит с диалогом дальше.

**Решение: остановленный диалог не запрещает боту слать в него сообщения.**
Как ведёт себя живой Max после `bot_stopped` — не измерено; мок шлёт событие
и не выдумывает ограничение, которого не проверял, — тот же принцип, что и
выше с `message`-кнопкой. Диалог, остановленный и начатый заново, снова шлёт
`bot_started`: контракт прямо говорит, что событие приходит, когда
пользователь «начнёт **или возобновит** общение с ботом».

## Клиенты и кнопки

Карточка клиента (создаётся в веб-чате кнопкой «+»): имя, фамилия, username,
телефон, координаты и `user_id`. Последний можно задать вручную — чтобы
воспроизвести на моке конкретного абонента из тестовых данных КЦ; занятый
отвергается `409 mock.conflict`.

Что из карточки куда доезжает — не очевидно и определяется контрактом:

| Поле | Куда попадает | Когда КЦ видит |
|---|---|---|
| `user_id`, `first_name`, `last_name` | схема `User`: `sender` у `message_created`, `user` у `bot_started` и `message_callback` | всегда (фамилия — даже пустой строкой) |
| `username` | там же | только если задан: пустой мок поле не присылает, как и прод |
| `phone` | только вложение `contact` (`vcf_info`), нормализованным: одни цифры, российский — с семёрки | по нажатию `request_contact` или отправке из чата |
| `latitude` / `longitude` | только вложение `location` | так же |

Телефона и координат в схеме `User` нет вовсе — это и есть причина, по
которой связывание абонента в КЦ идёт через `contact`: там в одном вложении
приезжают и телефон, и `user_id` (в `max_info`).

Поле `hash` вложения-контакта контракт описывает как признак «номер привязан
к аккаунту Max». Алгоритм живого Max не опубликован, поэтому мок считает
SHA-256 от нормализованного телефона: значение повторяемо между прогонами, но
**со стендом его сверять нельзя**. Длина при этом совпадает с продовой — 64
hex-символа.

Кнопки клавиатуры в веб-чате:

| Тип (inline / reply) | Что делает нажатие |
|---|---|
| `request_contact` / `user_contact` | `message_created` с единственным вложением `contact` |
| `request_geo_location` / `user_geo_location` | `message_created` с вложением `location`; при `quick: true` — без подтверждения |
| `message` | обычное `message_created` с текстом кнопки |
| `clipboard` | текст копируется в буфер, боту не уходит ничего |
| `callback` | `message_callback` с `payload` |
| `link` | открывает адрес |
| `chat`, `open_app` | не обрабатываются: первый требует группы `/chats`, второй — мини-приложения |

Контакт и геопозицию тестировщик может отправить и без кнопки от бота —
кнопками 👤 и 📍 рядом со скрепкой: обработку на стороне КЦ нужно проверять
в обоих случаях. Контракт требует, чтобы `contact` было единственным
вложением сообщения; мок это проверяет.

## Вложения

Двухфазная загрузка, как в реальном Max:

1. `POST /uploads?type=image|video|audio|file` → мок возвращает
   `{"url": "{public_base_url}/mock/upload/{token}", "token": "..."}`.
2. КЦ заливает файл на этот адрес (multipart или сырым телом). Формат ответа
   в OpenAPI-контракт не входит и повторяет документацию MAX:
   - `image` → `{"photos": {"photo": {"token": "..."}}}` — как в документации
     MAX; в `POST /messages` бот передаёт токен из словаря в `payload.token`
     (словаря `photos` в теле сообщения контракт не допускает);
   - остальные → `{"token": "..."}` — форма `UploadedInfo`.
3. Токен прикладывается в `POST /messages`.

Файлы, отправленные клиентом из веб-чата, доступны боту по ссылке
`{public_base_url}/mock/files/{token}` в теле события.

`config.example.yaml` — все поля со значениями по умолчанию. Переопределения
из окружения: `MAXMOCK_LISTEN`, `MAXMOCK_PUBLIC_BASE_URL`, `MAXMOCK_DB_PATH`,
`MAXMOCK_BLOB_DIR`, `MAXMOCK_TLS_CERT_FILE`, `MAXMOCK_TLS_KEY_FILE`,
`MAXMOCK_WEBHOOK_CA_FILE`, `MAXMOCK_WEBHOOK_INSECURE_SKIP_VERIFY`,
`MAXMOCK_LOG_FORMAT`, `MAXMOCK_LOG_LEVEL`, `MAXMOCK_LOG_BODY_LIMIT`.

`public_base_url` должен быть адресом, по которому мок доступен **со стендов
КЦ**: он подставляется в upload-адреса и ссылки на вложения.

## Консольный лог

Мок пишет в stderr строку на каждый вызов Bot API, каждое действие
тестировщика в веб-чате и каждую попытку доставки вебхука — вместе с телами
запроса и ответа. Этого достаточно, чтобы видеть работу интеграции, не открывая
UI и не заглядывая в базу.

```
level=INFO msg="Bot API" method=POST path=/messages query="chat_id=3003011655588571" status=200 ms=1 bot=1 chat=3003011655588571 req="{\"text\":\"Здравствуйте!\"}" resp="{\"message\":{...}}"
level=INFO msg="служебный запрос" method=POST path=/mock/api/dialogs/3003011655588571/actions status=200 ms=0 req="{\"action\":\"send\",\"text\":\"Не приходит смс\"}"
level=ERROR msg="вебхук →" type=message_created url=http://stand:8080/hook status=0 ms=0 попытка=1/3 bot=1 chat=3003011655588571 error="dial tcp: connection refused" event="{...}"
level=WARN msg="событие никуда не ушло" type=bot_started bot=1 chat=3003011655588571 причина="нет подписки на этот тип события"
```

Уровень строки поднимает статус ответа: `4xx` — `WARN`, `5xx` и несостоявшаяся
доставка — `ERROR`. Отказ виден и при `level: warn`, когда всё остальное
выключено.

Настройки — блок `log` в конфиге, флаг `-log-level` на один запуск, либо
`MAXMOCK_LOG_*` в окружении:

| Что | Значения | По умолчанию |
|---|---|---|
| `log.format` | `text` (key=value, для глаз), `json` (для сборщика логов) | `text` |
| `log.level` | `debug`, `info`, `warn`, `error` | `info` |
| `log.body_limit` | сколько байт тела попадает в строку; `0` — не печатать тела | `4096` |

`debug` добавляет фон: отдачу статики, страниц веб-чата и `/healthz`.

Что в лог не попадает: заголовки (а с ними токен бота в `Authorization` и
секрет подписки в `X-Max-Bot-Api-Secret`), тела заливаемых и отдаваемых файлов —
вместо них размер. Значение `access_token` в query-строке маскируется.
Обрезка тела касается только лога: обработчик всегда получает запрос целиком.

Подписки на `http://` принимаются, хотя контракт требует `https://`, — иначе
мок неприменим в закрытом контуре. В ответе на такую подписку приходит
пометка в поле `message`; как это устроено — «Послабление ради контура»
выше.

### TLS

Заданная пара `tls.cert_file` + `tls.key_file` поднимает `listen` по HTTPS;
пустой блок оставляет обычный HTTP. Порт один и тот же: второго слушателя и
редиректа с HTTP нет намеренно — поведение POST после редиректа различается
между клиентами, и для API это ловушка. При включённом TLS `public_base_url`
обязан начинаться с `https://`, иначе запуск останавливается: иначе стенды
получили бы ссылки на вложения по схеме, которой на порту уже нет.

Пара читается до начала обслуживания, а имена из SAN и срок годности
печатаются при старте — чтобы «стенд не подключается» разбиралось по логу,
а не через `openssl` на боевом хосте.

Обратная сторона — доставка на HTTPS-стенды КЦ. `webhook.ca_file` добавляет
удостоверяющий центр контура **к** системным корневым, не заменяя их: в
контуре часть стендов обычно на внутреннем CA, часть на публичном
сертификате. `webhook.insecure_skip_verify` отключает проверку целиком —
аварийная мера, о которой сервис предупреждает при каждом старте.

Подробности запуска, выпуск сертификата и разбор отказов — в
[docs/run.md](docs/run.md), обоснование решений — в
[docs/specs/2026-08-06-tls-design.md](docs/specs/2026-08-06-tls-design.md).

```

cmd/max-mock/ точка входа
cmd/validate-capture/ сверка снятых с прода тел с контрактом (см. ниже)
internal/
  config/     yaml + env
  ids/        chat_id, user_id, mid, токены
  wire/       структуры Bot API и событий
  specs/      загрузка контрактов и валидация
  store/      SQLite: боты, диалоги, сообщения, подписки, журналы
  events/     шина изменений для UI
  tlsconf/    конфигурации TLS: слушатель и клиент доставки
  webhook/    доставка событий на подписки
  core/       доменная логика
  maxfacade/  фасад Bot API
```

Идентификаторы генерируются в диапазоне до 2⁵², чтобы переживать разбор
JSON в JavaScript: `int64` больше `Number.MAX_SAFE_INTEGER` искажается и в
веб-UI мока, и в клиентах КЦ на Node.

## Обновление контракта

```bash
make sync-specs          # копирует yaml из ../maxapi и прогоняет тесты
```

Расхождения после обновления ловят валидация и `e2e/` — не тесты КЦ.

### Сверка контракта с живым Max

Тесты проверяют, что мок согласован с контрактом. Согласован ли **контракт с
платформой** — вопрос отдельный, и отвечает на него `cmd/validate-capture`:
он сверяет со встроенными схемами тела, снятые с боевого Max (регресс-прогон
описан в [`../maxbotdemo/README.md`](../maxbotdemo/README.md)).

```bash
# события webhook
jq -c 'select(.msg == "получено событие") | .payload' bot.log |
    go run ./cmd/validate-capture

# тела запросов к API — против именованной схемы
jq -c 'select(.msg == "запрос к API" and .path == "/messages") | .payload' bot.log |
    go run ./cmd/validate-capture -schema NewMessageBody
```

Команда грузит контракт **сырым**, без нормализаций из `internal/specs`:
правки, которыми мок обходит дефекты схемы, скрыли бы ровно те расхождения,
ради которых прогон и затевался. Цена такой слепоты уже известна — пока мок
дописывал `dialog` в enum `ChatType`, расхождения контракта с платформой не
видел никто.

События сверяются со **строгой ветвью** контракта (схема `WebhookUpdate`), а
не с телом операции: тело объявлено как `anyOf: [UpdateUnified,
WebhookUpdate]`, и плоская ветвь требует всего `update_type` и `timestamp` —
через неё регресс принял бы за корректные `message_created` без `message` и
`bot_started` без `chat_id`, отрапортовав «0 расхождений» на снимке, полном
мусора. Та же причина, по которой строгую ветвь берёт `ValidateWebhookBody`
(см. «Соответствие контракту»).

Первый прогон (2026-08-24, 19 событий) нашёл три бага контракта — заниженную
границу `seq`, отсутствующий `dialog` в `ChatType` и обязательный `username`
— все три исправлены в `maxapi`.

## Вне объёма

`/chats*`, `GET /updates` (long polling), `GET /videos/{videoToken}`;
групповые чаты и каналы; статусы прочтения (их нет в Bot API); искусственные
сбои; Docker и CI.

Эти пути отвечают `404` с кодом `mock.not_implemented` — честным отказом, а не
молчанием. Если приложение к ним обращается, скажите: архитектура их принимает
без переделок.

Дизайн и обоснования решений — `docs/specs/2026-08-05-max-mock-design.md`,
план реализации — `docs/plans/2026-08-05-max-mock-backend.md`.
